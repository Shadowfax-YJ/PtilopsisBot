# 收集插件维护

先读 [本仓库插件契约](../../../docs/plugins.md)，核对 `plugins.py`、`collector.py`、`runtime.py` 和 `config.py`。配置由管理员安装的 Python entry point 或本地配置文件提供，测试使用假 API/本地子进程。

将领域格式验证、OCR、业务去重和统计放在业务插件；宿主维护文件接收、基础校验、持久化投递、状态和可配置清理条件。新增插件默认不改变未启用插件的收集行为。

后台持续工作使用宿主 maintenance 钩子，生命周期和状态跟随机器人；业务依赖并入既有环境安装。验证安装发现、显式配置优先、未安装插件的基础行为、后台任务重启和超时恢复。

验收运行窗口时覆盖旧插件没有阶段进度、显式配置缺少 maintenance、长任务无输出和连续历史交接。后台启用状态与实际结果应可见，交接成功汇总与处理进度分别展示；不能用一条交接回执代替后台处理的验证。

验证稳定事件 ID、归档摘要、提交/回执持久化、超时和重启补投。收包完成与后处理完成分开；插件允许清理仍须满足既有本地/远端核验和用户配置，等待回执不占住下载任务。

宿主已有长期保留的 archive 可供插件直接引用，按插件契约传递保留承诺和来源路径。修改本地存储生命周期时先检查依赖引用；测试元数据或归档位置改变后的补投。业务插件负责自己的旧副本迁移，宿主继续维护原有归档、备份路径和通用收集行为。

修改插件协议时更新本仓库契约和通用测试，并检查已接入插件的兼容范围。BlackFlow 插件的权威位于已定位的 `lubiao-analysis`，跨仓库影响按其 `docs/data-pipeline/coordination.md` 处理；普通文件或消息功能不因此承担 BlackFlow 依赖。
