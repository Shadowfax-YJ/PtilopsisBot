# 下载、检查并保存 ZIP

Type: task
Status: implemented; live acceptance pending

## 实现

- 一个后台循环从 SQLite 取待处理记录，逐个下载。处理期间仍保留待处理状态；正常运行只启动一份机器人，不另建任务租约、执行历史或持久队列框架。
- 每次尝试都重新获取下载 URL，用 HTTP 流写入 `incoming/<记录ID>.part`，同时计算 SHA-256。检查 HTTP 成功、实收大小与 QQ 声明大小相等；有 `Content-Length` 时也要匹配。实收超过配置上限立即停止。
- 用 `zipfile` 检查目录和成员 CRC，不把 ZIP 成员解压到磁盘，不执行其中内容。拒绝加密包，最多 10,000 个成员，总解压量最多 2 GiB；先检查声明量，再分块读取并累计实际量，防止异常包耗尽资源。不另做路径规范化、压缩比规则和嵌套包解析。
- 有真实样本后增加一个检查必需文件和字段的普通函数。样本缺失时只做 ZIP 检查，日报用“已收集/唯一包”，不声称已验证游戏对局有效；检查规则无需版本化或保存配置指纹。
- 保存到 `archive/<上传日期>/<上传者QQ>/<记录ID>.zip`，原文件名留在数据库。`incoming` 与 `archive` 放同一个数据目录，完整文件改名后再把记录更新为收集成功，记录路径、大小、哈希和成功时间。
- 每次上传独立保存一份 ZIP，统计时按哈希去重即可；这会多占一些空间，但文件始终归属一条上传记录，省去共享文件引用和修复逻辑。
- 只保留四种处理结果：待处理、收集成功、检查不通过、处理失败，以及尝试次数和最近错误。网络、磁盘、数据库错误属于处理失败；确实不能读取的 ZIP 或缺少必需字段属于检查不通过，不写校验历史。
- 不通过或失败时清理本次 `.part`，保留源群文件及错误原因，允许之后手动重试。文件改名后记账失败的，下次重试可重新下载并替换该记录自己的目标文件，不扫描或认领其他文件。

## 完成标准

真实约 100 MB 包可以流式保存，同名重传不会覆盖另一条记录的文件。断网和重启后的待处理记录可以重新下载；损坏 ZIP、超限包和磁盘写入错误不会记为成功，也不会导致删除群文件。不承诺断电后数据库与文件始终一致。
