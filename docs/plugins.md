# 文件收集插件接入方案

状态：2026-09-11 已实现协议 1。`ptilopsisbot/plugins.py` 提供持久化队列和本地命令运行器；未启用插件时保持原有行为。

## 启用与状态

支持两种本地接入方式：

- 环境安装的 Python 包声明 `ptilopsisbot.plugins` entry point，名称为插件 ID，函数接收 `{protocol_version: 1, data_dir: 绝对目录}`，返回符合 PluginConfig 的字典。启动时自动加载，不读取上传包中的插件；不向 provider 提供 QQ token。安装包中的代码与宿主同权限。
- 已有 `plugin_configs = ["installed-plugin.json"]` 或 `[[plugins]]` 继续生效；显式同 ID 配置优先于自动发现，避免改写既有路径。`disabled_plugins = ["example"]` 可停用指定插件。重复安装声明或依赖缺失报出具体插件，不能悄悄退回未启用状态。

可选 `maintenance` 声明包含绝对 `command` 数组、`timeout_seconds`、`interval_seconds`。机器人运行时用独立后台任务发送 `maintenance.tick`，请求格式同下方协议，input 为空。即使没有新上传也持续处理，状态写入 SQLite，重启恢复未完批次，停止机器人时停止子进程。此任务与归档投递/下载独立，插件不要求另配系统定时任务。`status` 的 plugin_maintenance 展示结果、重试时间。

归档插件配置无 maintenance 时保持原配置摘要，已有交接回执继续有效。领域插件负责决定后台批次执行哪些工作，通用宿主不理解 OCR、快照或游戏字段。

请求包含 protocol_version=1、plugin_id/version、event_id、invocation_id、Unix 秒 deadline、hook=archive.committed、state_dir、input（archive_id/root/path/original_name/archive_relative_path/retained_locally/size/sha256）。`original_name` 来自收件记录，`path` 是宿主归档位置，`archive_relative_path` 是相对于宿主 archive 根的原路径，例如 `2026-09-09/123456789/735.zip`。插件保留来源目录和编号文件名，并把上传原名另作元数据。旧协议请求允许缺少新增字段。启动时补全历史请求；input 有变化时重新投递一次，包括新增元数据、保留承诺或迁移后的本地路径。输入不变的再次重启不会重复投递。宿主不把令牌或带签名下载 URL 传给插件。

`retained_locally=true` 承诺宿主在数据使用期间长期保留该 archive 文件。插件可以核对后持久化引用并直接读取，无需复制或创建第二套硬链接。现有自动清理仅删除群文件，本地 archive 继续保留；将来新增本地归档清理能力时必须先处理依赖引用，不能继续无条件发送该承诺。未声明此字段的旧宿主没有给出保留保证，插件可沿用独立冻结副本的策略。此字段是通用存储生命周期契约，业务去重、旧副本核对清理和原件索引仍由插件负责。

stdout 仍只返回最终 JSON。插件可在 stderr 输出以 `PLUGIN_PROGRESS ` 开头的一行 JSON，内容为 `{event_id: 本次请求 ID, message: 可读进度}`，每条立即 flush。宿主增量读取并显示在机器人原有运行窗口/日志；原样忽略其他诊断、格式错误或不同 event_id 的进度行，过滤控制字符并限制显示长度。响应必须原样返回 protocol_version 与 event_id，以及 ok/retry/unsupported/rejected；每个输出流总计仍最多 1 MiB。无需扩展的插件继续使用原协议，具体工作阶段与计数含义由业务插件提供。

启动时显示后台任务是否启用。后台子进程 15 秒没有有效阶段进度时，宿主输出运行耗时；插件恢复阶段输出后不追加这类提示。后台成功结果也会显示，连续相同结果去重；失败立即显示。历史交接成功每 5 秒或队列暂时清空时汇总，逐条回执保存在原数据库，详细成功消息为 DEBUG。响应可提供 warnings 字符串数组，宿主最多显示 10 条、每条 2000 字符；它只展示警告，不解释业务字段。缺失 maintenance 的显式配置会得到明确提示，继续保留用户原有配置和路径。

归档提交与插件事件在同一 SQLite 事务登记；`archive_staging` 恢复文件 rename 后中断的窗口。重启补投，使用事件与配置摘要去重。retry 自动退避，unsupported/rejected 等待人工处理；`ptilopsisbot plugin-retry RECORD_ID` 仅重试后处理。`status` 同时显示下载记录和独立插件状态。

required_for_cleanup=true 时必须收到当前归档摘要、当前插件配置对应的 ok + receipt.durable=true。它只表示插件承诺已持久化接收，不代表业务分析有效；对于长期保留的宿主原件，核验并持久登记引用即可，不要求另存一份文件。原有宽限期、本地/远端哈希核验仍需通过。等待插件不会占用下载名额。

通用文件策略可在 TOML 设置 `[file_policy]`、`name_pattern = '.*\.dat'`、`time_format = ""`、`validation = "bytes"`。默认仍匹配 run ZIP；ZIP/bytes 是宿主基础策略，具体领域校验交给插件。

## 宿主现有职责

`ptilopsisbot/files.py` 验证流式下载长度、计算 SHA-256、读取 ZIP 并限制成员/解压量。`collector.py` 登记上传、保存归档、统计贡献，按配置清理群文件；清理前重新验证本地和远端内容。`runtime.py` 管理扫描、下载、清理与回执，`config.py` 提供任务配置。

`collector.py` 使用可配置 FilePolicy 匹配名称、解析业务时间和选择基础校验；存储后缀来自已核验的原始文件名。业务时间与群上传时间保持独立，旧配置继续匹配当前包格式。

这些基础行为不依赖领域插件。收包成功、领域校验成功、后处理完成是不同状态，上传次数、唯一包数和分析样本数也分别展示。

## 建议新增的 Interface

- 文件策略：可选插件声明文件匹配规则、类型与校验策略，宿主保持下载大小、磁盘和路径限制。ZIP 检查作为内置默认策略复用，其他类型不被无条件强制解释为 ZIP。识别和 OCR 等长任务走提交后的后台交接。
- `archive.committed`：文件已落地并登记后投递稳定的归档事件，插件可入库、建索引、转交其他本地程序。
- 清理附加条件：配置可要求一个或多个插件的持久化交接回执；它是原有清理条件上的附加项，不授予插件远端删除能力。
- 插件状态查询与重投：失败/待适配/被拒绝分别展示，已完成下载保持完成；重复投递依赖稳定事件 ID 和输入摘要幂等。

已由 `ptilopsisbot/plugins.py` 管理运行，持久化投递与回执放在单独表中； `collector.py` 提交、恢复和清理检查，`config.py` 增加插件配置，`runtime.py` 管理独立后台任务，CLI/状态输出增加插件结果。宿主插件协议、配置迁移和测试归本仓库维护。

## 本地调用约定草案

首期优先配置受信任本地命令，以参数数组启动进程，通过 JSON 请求/结果交换数据。请求包括 `protocol_version`、`plugin_id`、`invocation_id`、稳定 `event_id`、钩子名称、归档 ID、路径引用、字节数、SHA-256、输出状态目录及超时。路径只描述本次本地输入，业务交付数据使用可移植对象引用。

响应具有 `ok`、`retry`、`unsupported`、`rejected` 等机器状态，附原因和结果引用。协议兼容、进程异常、超时及依赖缺失属于插件运行状态；它们不能改写成“ZIP 损坏”。业务返回的校验级别与回执在独立字段保留。

配置指定插件版本/协议范围、适用任务、超时、状态目录及是否参与清理条件。只有本地环境安装声明或管理员显式配置的插件运行；上传者文件名、压缩包和聊天内容不得决定可执行命令。插件不接收 QQ 连接密钥和远程删源接口。进程隔离用于控制故障传播，不作为权限沙箱。

## 投递、崩溃与清理

将上传记录的 `archived` 提交和 `archive.committed` 事件写入同一 SQLite 事务，之后异步投递。文件重命名与数据库提交之间仍存在退出窗口；恢复程序需验证已落地文件并补足登记，不能依靠回调只发生一次。

插件执行结果和中心输入回执持久化。重启补投未确认事件，重复入库不得增加上传贡献或重复发收包成功回复。新增插件失败不应占住下载并发，也不能把已经成功保存的文件退回下载失败状态。

清理仍要求 `auto_delete`、宽限期、明确归档成功、本地大小/哈希、远端重新定位和内容核验。启用额外交接条件后还要检查对应输入摘要的持久化回执。插件返回“允许”不能越过原有条件；没有回执/超时保持等待，并可在状态页定位。

“已排队”与“输入已可靠保存”分开。输入接收可在 OCR 之前完成；耗时识别不应成为收包回执的隐式前提。业务格式未知可以先保存原件，是否允许清理源文件由显式配置决定，不能标成业务验证成功。通知和删除行为的变更需沿用项目现有用户配置和消息规则。

## 领域插件如何接入

以 BlackFlow 为例，业务插件由 `lubiao-analysis` 维护，调用其入库入口，并复用采集程序发布的版本固定验证器。插件负责采集版本、原始/标准 schema、识别和可用专题；宿主仅显示插件提供的机器状态与摘要。

通用宿主源码不引入 BlackFlow 理念、楼层、游戏资源或特定分析仓库路径。插件随业务工具分发，宿主不打包 OCR 模型；插件升级通常不要求宿主升级，除非协议兼容范围变化。

机器人仓库中的旧 `archive-client/` 与独立 quark-timed-sync 是不同维护目标。当前同步联动以独立仓库为准，不把历史子项目自动纳入新插件实现。

## 验收

- 插件未启用时现有收集、重试、贡献统计和清理测试通过。
- 用独立于游戏字段的示例插件验证成功、重试、未知类型、拒绝、超时和缺少可执行文件。
- 在归档落地、登记提交、事件投递、中心回执各退出点恢复；重复事件不重复统计。
- 已保存但插件失败时下载状态不回退；配置了清理条件却无回执时不进入删源。
- 业务插件升级后可对同一归档重新评估，保留旧结果的方法版本，既有回执不错误套用于不同输入。
- 所有测试使用本地临时数据和模拟群接口，不以真实删群文件作为插件开发的默认验证步骤。
