# PtilopsisBot

已支持通用归档插件和后台处理，配置见 [插件协议](docs/plugins.md)，维护入口为 [extend-collector-plugins](.agents/skills/extend-collector-plugins/SKILL.md)。

一个采用《明日方舟》干员白面鸮说话风格的 QQ 群对局数据小助手。将 `run-YYYYMMDD-HHMMSS-NNNNNN.zip` 下载到本机，检查完整性，再清理对应群文件腾出空间。每个实例配置一个目标群，只主动收集根目录中的对局包。

本仓库仅维护 QQ 群数据收集机器人。夸克网盘定时订阅工具在独立仓库 [quark-timed-sync](https://github.com/Shadowfax-YJ/quark-timed-sync) 维护。

本项目为社区独立项目，原创代码采用 [MIT 许可证](LICENSE)。第三方组件及角色相关权利说明见 [NOTICE.md](NOTICE.md)。

## 安装与启动（Windows / Python 3.11+）

在同一台 Windows 电脑上运行 NapCat 和机器人，通过本机反向 WebSocket 连接，无需公网 IP 或端口映射。示例目录为 `D:\Bots\PtilopsisBot`。

安装 Python 3.12 和 Git 后执行（已有项目时用 `git pull` 更新）：

```powershell
git clone https://github.com/Shadowfax-YJ/PtilopsisBot.git D:\Bots\PtilopsisBot
cd D:\Bots\PtilopsisBot
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e .
if (-not (Test-Path config.toml)) { Copy-Item config.example.toml config.toml }
.\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(32))"
```

收集 BlackFlow 并自动后处理时，同一次环境安装使用 `pip install -e '.[blackflow]'`，会带上固定版本的 analysis 业务插件与 OCR。照常启动机器人，即持续验证、补识别，每天北京时间 00:05 将截至前一日入库的数据发布到实际 data_dir 下的 `blackflow/published`，版本按实际发布时间 YYYYMMDD-HHMMSS 命名；夸克备份选择该目录。基础安装仍供其他收集场景使用。后处理无需额外安装器、独立进程或 Windows 任务。

首次配置时，将 `config.toml` 中的 `group_id = 0` 替换为自己的目标 QQ 群号，再把生成的随机值填进 `access_token`。示例中的 0 是占位值，未填写真实群号时不能启动。已有配置保留原值即可。配置和数据目录不会提交到 Git：换电脑需单独带上 `config.toml`；已经收集过数据时先停止旧进程，再完整复制 `data` 目录。新电脑重新建立 `.venv`，不要复制旧虚拟环境；数据目录换位置时同步修改配置里的 `data_dir`。

1. 从 [NapCat 官方发布页](https://github.com/NapNeko/NapCatQQ/releases)选择适合 Windows x64 的安装包，按照[官方配置说明](https://napneko.github.io/config/basic)完成安装和 QQ 登录。NapCat 放在独立目录，例如 `D:\Bots\NapCat`；版本兼容限制见下文。
2. 打开 NapCat 启动日志给出的 WebUI 地址（默认端口 6099），使用日志里的随机 Token 登录，按界面提示修改 WebUI 密码、扫码登录 QQ。账号需要加入 `config.toml` 配置的目标群；删除其他成员的群文件需要群管理权限。NapCat 无需申请启动授权，WebUI 密码在本机生成。见 [官方配置说明](https://napneko.github.io/config/basic)。
3. 在 NapCat 的网络配置中新建并启用 **WebSocket 客户端 / 反向 WebSocket**：URL 为 `ws://127.0.0.1:8080/onebot/v11/`，消息格式选 `array`，Token 填 `config.toml` 中 `access_token` 引号内的值。这个连接密钥与 WebUI 登录密码用途不同。只需这个 OneBot 11 连接，无需另开 HTTP API。
4. 运行机器人：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m ptilopsisbot run
```

修改配置后重启。示例配置为 `auto_delete=true`、`history_delete_grace_hours=0`、`delete_grace_hours=12`：历史积压归档后立即进入待清理队列，通过本地、远端校验后删除；未触发容量清理时，新上传的包从首次成功归档起保留至少 12 小时。清理任务约每分钟检查一次到期记录，也会在归档或补扫后检查。旧配置若未填写 `history_delete_grace_hours`，历史包沿用 `delete_grace_hours`，保持原来的统一宽限期；未填写 `delete_grace_hours` 时仍默认 24 小时。启动补扫会收集根目录里已有的符合条件的包。

修改保留期会按原有归档时间（重复候选使用已记录的较晚保护起点）重新计算所有待清理文件的期限，不从修改或重启时间重新计时。例如从 24 小时改为 12 小时，原剩余时间减去 12 小时；还剩 20 小时的变成 8 小时，还剩 6 小时的已到期，会在下次通过校验后清理。其他尚未到期的文件继续等待，已登记为新上传的文件不会因为重启而改成历史包立即清理。独立配置为 0 的历史包期限不受此项修改影响。

`group_storage_limit_gib = 8` 启用容量清理（8 GiB = 8,589,934,592 字节）；未配置时关闭。每轮先处理通常的到期文件，再汇总群根目录及所有子文件夹的文件大小。超过阈值时，按上传时间从旧到新清理 bot 已成功归档的根目录对局包，允许提前结束 12 小时保留期；上传时间缺失时采用已登记的首次发现时间，重复候选采用较晚的保护起点。该阶段逐个核验、删除并重新统计，降到阈值以内即停止。阈值统计的是群文件占用，本地归档不参与该阈值计算。

容量清理仍要求本地归档大小与完整 SHA-256 正确、远端内容与归档一致，并确认群文件确实消失；实际删除前会再次统计占用，校验期间有人腾出空间后便可停止提前清理。安装包、视频、子文件夹中的文件等计入总占用，清理范围仅限 bot 已成功归档的根目录对局包。容量仍超限但没有可安全清理的包时记录原因，等待后续归档或人工处理。容量统计失败、字段不完整或任何目录达到 1000 项扫描上限时暂停容量清理，按时间到期的普通清理仍可独立运行。关闭 `auto_delete` 会同时关闭两种清理。

`status` 中的 `group_storage_bytes` 是最近一次统计的群文件字节数，`storage_checked_at` 是统计时间，`storage_cleanup_error` 是统计失败或无法继续清理的原因；未知容量返回 `null`。NapCat 的容量接口曾在群里有文件时返回 0，因此容量检查使用实际文件列表汇总，并与补扫、普通清理共用分页查询锁。文件列表汇总值与 QQ 界面显示可能存在更新延迟或单位差异。

另开终端运行下方 `status` 命令，看到 `"online": true` 后上传真实游戏 ZIP 进行验收。正常运行只启动一份小助手。

## 平时怎么用

机器人常驻时，在另一个终端执行：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m ptilopsisbot status
.\.venv\Scripts\python.exe -X utf8 -m ptilopsisbot scan
.\.venv\Scripts\python.exe -X utf8 -m ptilopsisbot retry 12
.\.venv\Scripts\python.exe -X utf8 -m ptilopsisbot report 2026-09-05
.\.venv\Scripts\python.exe -X utf8 -m ptilopsisbot report 2026-09-05 --preview
```

`status` 查看连接和最近 50 条上传记录，`active_downloads`、`active_cleanup` 分别列出正在下载和清理的记录 ID；`scan` 请求补扫并检查到期清理，返回 `queued` 后由后台执行；`retry` 使用上传记录 ID 重试，正在下载或清理的记录需等本次操作结束；`report` 发回目标群，指定日期无新增唯一包时返回 `skipped` 并保持群内静默；`--preview` 只在本机查看文案或跳过原因。命令通过同一个本机端口和 token 操作正在运行的机器人，不会启动第二个下载进程。正常 Ctrl+C 停止即可暂停采集和清理；正在进行的本地文件检查会先结束并关闭文件。被中断的下载不消耗失败重试次数，重启后从头下载。

上传通知触发根目录补扫；连接、重连及每 30 分钟也会补扫。扫描、下载和清理使用独立的异步任务，ZIP 检查和本地哈希计算在线程中执行。所有任务共用群文件列表查询锁，确保同一时刻只有一次完整分页查询，避免 NapCat 并发查询时混入重复页面；下载流不持有该锁，仍可并行。单次请求最多 1000 项，达到上限会提示日志，不承诺完整枚举更大的根目录；包需直接上传到根目录，不收集子目录。下载或 ZIP 检查失败每隔 5 分钟重新定位源文件并从头下载；`download_max_attempts = 3` 控制总尝试次数（含首次，范围 1–10），默认首次加 2 次重试。网络错误和 ZIP 错误共用次数，重启和重复补扫不会清零。未通过 ZIP 检查的内容不归档、不计入日报、不删源；还有次数时记为 `failed`，最后一次仍未通过则记为 `invalid`。旧版提前标为 `invalid`、尚未归档且仍有剩余次数的记录会在启动时自动恢复，保留已用次数和原重试时间。耗尽次数后查看原因，处理完可用 `retry` 手动开启新一轮尝试。启动日志和 `status` 显示次数上限，失败日志显示已尝试次数及是否还会自动重试。每轮处理和远程操作前检查 QQ 在线状态，掉线暂停，不消耗单个文件的重试次数。

程序主动检查发现的失败会记录具体原因，例如源文件匹配项数或下载大小不符；第三方异常继续只记录类型和 HTTP 状态码，避免保存临时下载地址或 token。升级后首次启动会为当前群旧版仅记录 `ValueError`、尚未归档且未删源的 NapCat 失败记录恢复一次重试机会；恢复标记持久化，之后重启不会反复重置次数。其他错误、已归档数据和已删源记录不受影响。

下载默认同时处理 3 个包，可在 `config.toml` 中设置 `download_concurrency = 3`（范围 1–6，修改后重启）。大于 1 时保留一个名额给本次连接收到文件消息、且与根目录唯一匹配的新包；其余名额也优先新包，没有新包时处理历史积压。默认因此最多同时下载 2 个历史包，并能立即接纳一个新包；设置为 1 时下载串行，仍优先尚未开始处理的新包。已经开始的下载不中途抢占，重连或重启后旧任务按历史积压处理。清理使用独立的并发池，不占上述下载名额，同一记录的回执处理结束后才可进入清理。

`cleanup_concurrency = 3` 控制同时进行删源校验的包数（默认 3，范围 1–3，修改后重启）。每个包仍先检查本地归档，再完整读取远端计算 SHA-256；校验可并行，实际删除及删除后的确认逐个执行，删除请求也不会与根目录分页查询重叠。HTTP 连接池按下载与清理名额之和设置。等待删除锁后会重新检查环境与保留期限，迟到的新上传证据仍能阻止提前删除。单包校验失败不妨碍其他包；磁盘或数据库故障会取消并等待本轮其他清理任务结束，Ctrl+C 同样会等本地读文件线程退出。`status` 中的 `cleanup_concurrency` 和 `active_cleanup` 可查看并发配置及正在清理的记录。

删除保留期与下载优先级分别管理。首次连接或重连的根目录快照里，缺少上传时间且没有当前文件消息的文件，以及 QQ 上传时间早于本次连接的文件，按历史来源首次登记；能对应当前文件消息、QQ 上传时间在连接之后，或初次快照后才发现且缺少上传时间的文件，按新上传保留。识别结果写入 `source_kind`（`history` / `live` / `unknown`），新包不会因回执已发送、重连或重启而变成即时清理。消息迟到可以把历史分类提升为新包；远端哈希校验后还会重新检查保留期限。旧版记录中只有消息时间能证明是新包的会自动标为 `live`，其他无法确认来源的旧记录保留 `unknown`，使用新包宽限期。`status` 显示这项分类及 `delete_after` 最早清理时间；通常从首次成功归档计算，重试不重复计时。同一登记键又出现重复候选时，从本轮重复候选的发现时间与首次归档时间中的较晚者起算；重复补扫、普通重试和重启不会反复延长。等待清理期间又出现更新的候选则延长保护，相关时间写入数据库。

每天北京时间 00:05 检查前一天的收集情况，有新增唯一包才发日报。报告包含截至统计日期的数据总量、当天上传的新增量（均为按完整 ZIP 的 SHA-256 去重后的包数和 ZIP 容量），并感谢当天成功收集到数据的群友，每人列一次；参与重复上传的群友也会列入当日致谢。相同内容只算一份新增数据，归属首次收集成功的上传记录及其上传日期；仅重复上传、只有失败或待处理记录、没有上传时都不发日报。迟到完成和离线漏发可手动重发。当前只检查 ZIP 可读性，待真实游戏样本到位后补必需文件与字段检查。

下载和删源前的远端校验每 10 秒输出已完成比例、MiB 和平均 MiB/s；完成时记录耗时，ZIP 检查与本地哈希校验也分别记录耗时。没有程序限速，但每个成功清理的包通常需读取远端两次。并发可以减少下载和清理排队等待，不保证总带宽随并发数成倍增加；启用收包回复时，仍在该包下载、检查和归档成功后发送。`queued` 且 `attempts>0` 也可能表示正在下载，可用 `active_downloads` 和阶段日志判断。

## 群内回复风格

修改或新增群内回复时，沿用以下约定。参考游戏内中文[语音记录](https://prts.wiki/w/%E7%99%BD%E9%9D%A2%E9%B8%AE/%E8%AF%AD%E9%9F%B3%E8%AE%B0%E5%BD%95)、[角色档案](https://prts.wiki/w/%E7%99%BD%E9%9D%A2%E9%B8%AE)，以及[《深暗之梦》](https://prts.wiki/w/白面鸮/干员密录/1)、[《日记本》](https://prts.wiki/w/SA-ST2_日记本/NBT)的对白。链接为玩家 Wiki PRTS 收录的官方文本转录；本助手文案为适配收包场景的原创表达。

- 白面鸮是有情感的医疗干员与数据维护员。保持冷静、礼貌和含蓄的关心，以短句说明对象、状态和结果；自称可以使用“白面鸮”。
- 收包回执先明确对象和保存状态，再简短感谢提供数据的人；可用句号形成轻微停顿。保留“谢谢您”“辛苦了”等自然表达，避免“感谢上传”“感谢支持”等平台提示或通用客服措辞，不要求每条都带自称或术语。
- 保留确认、判断、结果式的表达和自然道谢。“检索”“数据汇总”“校验”等技术用语以语义贴切、对应实际工作为准，不机械限制数量，也不为增加角色感而堆砌。句子保持自然、信息完整，不必每句都拆碎。
- 数字、失败原因和处理建议准确优先。“数据汇总完成”只说明统计完成，不能把仍待处理的包说成已归档，也不能把 ZIP 可读说成游戏内容有效。回执也适用于内容重复的上传，不将每次收包都描述为“新增数据”。
- 游戏台词中确有系统、休眠与数据库相关表达，也有冷幽默和自主判断；这些特点本身不等于 OOC。本助手的操作通知只在真实对应状态下使用休眠、故障等措辞，成功回执不插入初始化数据库或权限变化的玩笑。这是为了避免用户误判收包状态，并非人物不会这样表达。
- 使用“您”或成员昵称，不默认所有群成员都是博士。表达克制，不加入卖萌口癖、网络谐音梗或擅自补写人物关系与经历。
- 日报开场使用“本次”或直接描述收集记录，数据与致谢行使用“当日”指代统计日期。定时日报在次日发送，也可能手动补发历史日期，不使用“今日”或“昨日”作固定称呼。保留群内称呼“MAA 训练家”。

`send_receipts = false` 关闭逐包收包回执，归档、清理、新包识别和日报照常工作；示例配置已关闭回执，未配置此项的旧配置仍默认开启。修改配置后重启机器人生效，启动日志和 `status` 会显示开关状态。关闭期间收集的包以后也不会补发回执。

群内通知包括可选的逐包回执、日报和里程碑公告。启用回执时，在线收到的新对局包首次下载、校验并成功归档后，引用对应的文件聊天消息，用简短的一行确认保存并致谢；次日有新增唯一包时发送日报。回执不再重复文件名、QQ 号和检查说明，日报只展示总量、当天新增量和群友致谢，不附加发现日期说明。回执和日报开场各有 8 套文案，每次从对应模板池随机选择，允许偶尔重复；日报的数据与致谢行共用同一格式。模板位于 [ptilopsisbot/messages.py](ptilopsisbot/messages.py)，没有接入闲聊模型。

`milestone_interval = 500` 启用每 500 份数据一次的里程碑公告；省略该项则关闭，与 `send_receipts` 和 `auto_delete` 独立。以当前群已成功归档内容的唯一 SHA-256 数量为准，重复 ZIP、失败和等待下载的记录不增加数量，归档后的群源文件删除不减少进度。首次启用记录当前数量为起点，不补发此前已跨过的档位。启用后的新归档（包括补扫收集）达到下一档时发送；如果离线或暂停期间跨过多档，恢复时只公告当前达到的最高档，避免连发。公告使用独立任务，不占用下载名额或阻塞清理。

里程碑进度按群写入 SQLite，重启、补扫和配置间隔调整不会清零。发送前持久记录已领取的档位；同一档只尝试发送一次。若发送超时、失败或进程在发送期间退出，QQ 可能已收到消息，因此保留结果未确认的记录，不自动重发该档；这不会阻止后续里程碑。`status` 的 `milestones` 显示 `interval`、`unique_count`、`next_threshold` 和最近一次公告结果 `latest_announcement`（`sending` / `sent` / `uncertain`）。正常离线时不领取档位，等待重新在线。

```text
白面鸮确认：对局数据累计收录已达 1,000 份。
感谢各位 MAA 训练家提供数据。辛苦了。
```

**首次进群、启动、重连和手动补扫发现的历史文件静默收集，不逐包回复，也不补发历史日报。**这些文件照常归档和统计，并按已登记的来源及对应宽限期清理群文件。上传日期缺失时采用下文的发现日期规则。

引用使用 NapCat 文件聊天消息的 `message_id`，不是文件通知里的临时 `file_id`。只使用本次连接期间收到的新文件消息，并要求上传者、文件名、大小与根目录文件唯一对应；根目录有有效上传时间时，还要求本次连接后上传、与消息时间相差不超过 60 秒。上传时间为 `0` 或缺失时，使用当前文件消息匹配，不再误判成 1970 年的历史文件。找不到对应消息、消息在归档后的回执检查结束后才到达，或存在歧义时保持静默；实际引用气泡的显示由 QQ 客户端决定。消息引用只在内存中保留最近 1000 条，断线或重启清空，不追补跨重启的收包回复。

重复通知、补扫、重启或对同一份已收集数据手动重试不会重复发送收包回复。另一次可区分的新上传也可以收到自己的回复，包括内容重复的 ZIP。归档失败或检查不通过时不发成功回复。发送失败只记日志，不影响收集与清理，不建立通知重试队列；日报可以手动补发。

成功发送后日志会写明“收包回复已发送”、源文件消息 ID 和回复消息 ID；静默跳过与发送失败也各有记录。QQ 的撤回通知中，`user_id` 是被撤回消息的发送者，`operator_id` 是操作者，可据此区分文件消息与机器人回复。

示例：

```text
对局包已保存。感谢您提供数据。
```

```text
白面鸮已完成本次数据汇总。
统计日期：2026-09-05。
数据总量：100 个包，共 9.8 GiB。
当日新增：5 个包，共 500.0 MiB。
感谢当日上传数据的 MAA 训练家：小张、小李。
```

## 保存和清理规则

- 文件保存为 `data/archive/<统计日期>/<上传者QQ>/<记录ID>.zip`；每次上传独立保留，原名和 SHA-256 在 `data/collector.sqlite3` 中。统计时间优先使用 QQ 上传时间，缺失时使用可唯一匹配的文件消息时间，否则使用首次发现时间；`status` 中的 `time_source` 分别为 `qq`、`message`、`observed`，群内日报不展示此说明。不把文件名里的对局时间当成上传时间。
- 旧版误存为 `uploaded_at=0` 的记录在启动时自动修正：使用已保存的观察/归档时间，并移动原归档、更新数据库路径，保留记录 ID、哈希和删源状态。真实上传日期无法从 `0` 恢复，修正值标记为 `observed`。若遇到目标文件冲突或归档缺失，会保留现场并记错误，不覆盖已有文件。不要手动只改目录名，否则数据库路径会失效。
- NapCat 的 `file_id` 是临时缓存引用，不能跨重启保存使用。本助手按群号、busid、上传者、原名、大小、根目录原始上传时间生成登记键；推定的统计日期不会改变登记键，避免补扫或重启重复计数。同名但原始上传时间不同的包仍分别登记。对于同一登记键下的重复候选，使用核对前的修改时间选择最新一份，先下载、检查 ZIP 并归档；修改时间只用于候选排序，不作为上传时间或登记键。时间缺失、最新时间并列，或无法确认完整列表时保留文件并记日志。
- 开启 `auto_delete` 时，同一登记键的重复候选会进入去重清理：先重新检查本地归档，再完整读取整组远端文件计算 SHA-256。全部与归档一致后，立即删除旧副本，不等待普通保留期；每次使用刚刚核验过的临时 ID，逐个删除并确认剩余候选正好符合预期。任一候选内容不同、本地损坏、校验期间列表改变、掉线或环境不可用时停止删源。保留的最新一份继续按来源执行配置的宽限期：示例配置中历史包归档后可立即清理，新上传包保留 12 小时。连接期间观察到重复候选增加、最新候选时间变大或对应当前文件消息时，保守地按新上传保留；消息有歧义时不发回执。同一登记键只登记一条记录，不重复计入新增量。`status` 的 `duplicate_pending` 表示尚需核对重复候选。
- 按时间触发的普通删源必须已收集成功、经过宽限期，且本地文件大小和重新计算的 SHA-256 都正确。随后重新枚举根目录定位唯一候选，用新 ID 获取远端内容并再次计算 SHA-256，与归档一致后才用该 ID 删除。容量超限时可以提前结束宽限期，但仍执行同样的本地、远端校验及删除确认。**每个成功清理的包通常下载两次**，第二次只计算哈希，不另存副本；失败包、本地损坏、候选冲突或内容变化时保留群文件。
- QQ 删除结果必须明确为成功，并在删除后的完整根目录列表中确认源文件已消失，才记 `deleted_at`。最多补查 3 次、间隔 1 秒；仍存在、列表字段不完整、达到扫描上限或查询失败时保留待清理状态。删除前暂时找不到源文件（可能已移动或超出扫描范围）也不当作已清理。
- 删除前根目录匹配 0 项时，记录 `source_missing_at` 并转为等待补扫，只提示一次；普通到期清理和容量清理都会跳过该记录，不反复读取本地归档或查询源文件，重启后仍保持等待。启动、重连、每 30 分钟或手动 `scan` 的补扫再次发现同一源文件后，自动恢复本地和远端核验；`retry` 也可清除等待状态。归档、数据统计及原保留期均保留，不把缺失视为删除成功。旧版已记录的“匹配 0 项”和“找不到重复文件”也会自动转入此状态；候选冲突、哈希不符和接口失败仍正常报警。
- 补扫再次发现已标记删除的源文件时，会自动恢复待清理状态，再验证本地和远端大小/哈希后重试，不重复归档、计数或发送收包回复。内容不同或本地归档损坏时保留源文件；相同登记键的重复候选按上述规则核对并保留最新一份。
- 实测删除群文件会联动撤回对应的文件聊天消息，出现“管理员撤回了一条消息”。PtilopsisBot 没有调用 `delete_msg`；NapCat v4.18.19 的[删除群文件接口](https://github.com/NapNeko/NapCatQQ/blob/v4.18.19/packages/napcat-onebot/action/go-cqhttp/DeleteGroupFile.ts)及其[QQ 内核调用](https://github.com/NapNeko/NapCatQQ/blob/v4.18.19/packages/napcat-core/apis/group.ts#L332)没有“保留聊天消息”参数，因此目前不能保证静默删文件、保留原文件气泡。延长宽限期只推迟清理，不保证取消撤回联动。
- 本地空间低于 2 GiB、账号离线或数据库不可写时暂停下载与清理。修复后自动继续；日志位于 `data/collector.log`，最多保留约 20 MiB。
- 本地文件不自动清理。需要备份时停止机器人，复制整个 `data` 目录；仅有本地一份副本时，磁盘损坏仍可能丢失数据。

### NapCat 版本兼容

机器人通过 NapCat 的扩展接口获取、定位和删除群文件，不承诺兼容所有 OneBot 实现。NapCat 升级后，应先在测试群核对上传、归档、根目录枚举和删源确认。

NapCat v4.18.19 的发行包曾将 QQ 内核删除参数固定为 `busid=102`，而部分群文件使用 `104`，导致接口报告成功但源文件仍存在。机器人会传递真实 busid，并在删除后重新检查；使用存在该问题的版本时，可能一直保留待清理记录。应使用能够正确处理实际 busid 的 NapCat 版本，并对真实群文件验证。上游实现参见[删除接口](https://github.com/NapNeko/NapCatQQ/blob/v4.18.19/packages/napcat-onebot/action/go-cqhttp/DeleteGroupFile.ts)。

公开仓库不分发 NapCat 修改版或补丁。更新此仓库不会修改已安装的 NapCat；已有部署的兼容性取决于本机安装版本。

## 可选：整台机器登录后自启动

正常手动启动机器人即可运行全部后台后处理。以下只用于需要整套机器人和 NapCat 随登录启动的情况。

关闭 Windows 接通电源时的自动睡眠。用任务计划程序新建一个登录触发的任务，程序为 `powershell.exe`，参数为 `-NoProfile -ExecutionPolicy Bypass -File "D:\Bots\PtilopsisBot\start.ps1"`。设置“如果任务已在运行，不启动新实例”，并关闭默认的运行时长限制。NapCat 也要设置启动并保持 QQ 登录；先分别手动跑通，再配置自启动。
